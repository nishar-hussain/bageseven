# Developer integration

## One customer billing embed

Configure the unified billing experience at `/app/builder`. Choose the provider's active plans, edit copy and styling, preview desktop/mobile, then Save draft or Publish embed. The live preview uses a short-lived token for the signed-in provider's own account. Payment, allowance and renewal-cancellation transactions still require explicit wallet approval. Builder preview does not fabricate customers, grants, prices or successful payments.

React installation uses the existing `@bagseven/sdk/react` workspace package and passes `component="cmp_customer"`, selected `planIds`, theme and the holder-scoped customer token. The SDK includes wallet connection and navigation between Plans, My access and Checkout; a host can still supply a custom `walletSlot`. `initialView` controls the starting section; a supplied checkout session opens Checkout. React code contains the chosen configuration as a snapshot; copy it again when changing that installation's styling.

Website installation references the published design at `/embed?design=<uuid>&parent=<merchant-origin>`. Its JavaScript listens for `bagseven:ready`, fetches `/api/billing/customer-token` from the merchant's authenticated backend, then sends `{type:"bagseven:authorize", token, holder, checkoutSessionId?}` to the iframe. The customer-token endpoint is implemented by the merchant: authenticate its current customer, call the Node SDK's `identify({holder, expiresIn:900})` using a server-side secret key, and return the token with that same holder. Never accept an arbitrary unauthenticated holder from the browser. Return `Cache-Control: no-store`; never expose the secret API key. Both sides validate exact origins and window sources, and the iframe requests refreshed credentials every fourteen minutes. New installation snippets never place tokens in URLs or saved designs. A standalone published page can show public plans; customer actions need the authenticated host integration.

Builder's “Preview published embed” exercises this same iframe authentication channel using the provider's own preview account. Drafts and published snapshots were introduced in migration 0020. Apply all migrations through 0024 before deploying the current console. The public design endpoint returns only the published configuration and never its owner, drafts, customer email or credentials. Published plan IDs are validated against the provider's active catalog. Existing `/embed?component=...` links and React component IDs remain compatible.

Use the existing `@bagseven/sdk` workspace package for entitlement checks, consumption, checkout and embedded billing. Browser traffic goes through the console BFF; secret API keys and daemon tokens remain on the backend. Publishable keys support permitted reads, and customer tokens are holder-scoped.

Configure `AVALANCHE_NETWORK=fuji`, `AVALANCHE_CHAIN_ID=43113`, and `AVALANCHE_RPC_URL`. Set the exact six-decimal stablecoin contract as `AVALANCHE_USDC`. Network, receipt token, payer, recipient, amount and confirmation depth must match before access is issued. No token address or successful payment is synthesized.

Browser helpers exported from `@bagseven/sdk/wallet` are `connectAvalancheWallet`, `authorizeAvalanchePayment`, `payStablecoinOnAvalanche`, `subscribeOnAvalanche`, `cancelAvalancheSubscription`, and `renewSubscriptionAllowance`. Checkout supplies its configured token address. Funding, allowances, subscription creation and cancellation require wallet approval.

The registry store implements all GrantStore methods. Decimal credits use 18-decimal atomic units and are bounded by uint128. Private metadata is scoped by chain, contract and grant key. Contract consumption IDs prevent duplicate decrements; reservation finalization cannot both commit and release. Registry writes use the provider's authorized signer and a durable signed-transaction journal.

Discovery filters run in PostgreSQL against indexed holder, feature, worker and expiry fields before bounded parallel contract reads. Renewal workers select at most 100 due subscriptions per cycle, honor retry delays and use database advisory locks to coordinate collectors. Payment and entitlement writes remain independently journaled before broadcast.

In a separate test checkout, explicitly select Anvil with `pnpm setup -- --anvil`, then run `pnpm start:local`, then `pnpm mcp:local`. To populate one explicitly selected local workspace, set `LOCAL_PROVIDER_EMAIL=your-email` when running `pnpm seed:local`. This creates three receipt plans, provider gas authorization funded with local test AVAX, and three contract-backed grants. It does not create a customer subscription or allowance. Local wallet payments must use the configured Anvil RPC at `http://localhost:58545` with chain ID 43113; public Fuji RPCs cannot see Anvil contracts. Use public Anvil development accounts only. Keep the Anvil database and addresses separate from Fuji deployment configuration.

For local offline unit tests only, explicitly select `ENTITLEMENT_STORE=memory`. Production requires `ENTITLEMENT_STORE=avalanche`, a deployed registry, `DATABASE_URL`, and `ENTITLEMENT_SUBJECT_SECRET`. Apply migrations through 0024. Do not rotate the subject secret without an explicit identity migration.

The existing receipt app runs with `pnpm demo:dapp` on ports 5177/5178. Set `DEMO_PROVIDER_ID` and `DEMO_HOLDER` to the verified-email local fixture; merchant requests use `PROVIDER_SCOPE_SIGNING_KEY`, and active plans are selected by provider and feature rather than hardcoded names. `pnpm --filter @bagseven/demo-dapp seed:demo` explicitly creates missing feature access on local Anvil using the provider-funded registry signer; it requires the known Anvil provider owner, refuses public RPCs and never creates a customer subscription. Reloading the app does not mint access or refill credits. `pnpm demo:check` performs actual OCR, consumes one local scan credit, one JSON export credit and one insights credit, verifies retry safety and checks that backend and browser SDK balances agree. Pro CSV export checks access without decrementing its boolean grant. Pricing marks a monthly plan current only from an actual non-terminal subscription for that plan; possessing prepaid feature credits does not disable checkout.

Local acceptance commands include `pnpm smoke` and `pnpm smoke:mcp` for authenticated reads, `node --env-file=.env scripts/test-provider-gas.mjs` for provider authorization boundaries, `node --import tsx scripts/test-subscriptions-local.mjs` for real isolated renewal transactions, `node --env-file=.env --import tsx scripts/test-subscription-persistence.mjs` for durable recovery, and `pnpm test:x402` for isolated mandate-funded EIP-3009 settlement, reconciliation and refunds. The persistence/x402 tests create and remove their own local test databases; they do not require your private keystore or public Fuji funds.

MCP tools include status, entitlement checking/consumption, `buy_access`, checkout creation, `paid_run`, renewal cancellation, denial explanations, and bounded `bagseven_fetch` payments. Remote clients use HTTPS streamable HTTP at `/mcp`, OAuth PKCE, and email-code plus wallet-signature consent. Agents receive Bagseven tokens and never receive inbox credentials or wallet private keys.

OAuth sessions are bound to the verified email, signed wallet and client. Holder-scoped grants and subscriptions cannot be accessed through another account's login; new spending requires the signed wallet to own the bound worker's mandate. A legacy static operator credential is service-level authority, not customer OAuth. Keep it disabled in the public runtime and never expose it to remote clients. OAuth credentials and consent are shared through PostgreSQL, with atomic single-use code/refresh exchanges and shared attempt limits. HTTP requests use stateless transports; no process-local session map or replica affinity is required.

Verify with `pnpm test`, `pnpm typecheck`, and `node scripts/test-entitlement-registry.mjs`. Rebuild contract artifacts with `node scripts/compile-entitlement-registry.mjs` and `node scripts/compile-subscription.mjs` after contract changes.

## Isolated x402 payments

Use the existing Agent spending page to approve a payment authority for an active provider-bound mandate and agent. Connect that mandate's owner wallet and review the exact chain, token, merchant, HTTPS resource origin, per-payment ceiling and expiry before signing. This approval transfers no funds. Configure a separate, backed-up `X402_PAYMENT_ENCRYPTION_KEY` on the daemon only. AES-GCM binds each encrypted key to its authority. `X402Keyring` allows replacement with a KMS/HSM backend without changing payment orchestration. Do not reuse gas-encryption or provider-scope keys.

`X402_FACILITATOR_URL` defaults to PayAI. Its standard v2 adapter probes network support; approval also probes the configured token's EIP-3009 interface. Adding a facilitator means implementing `X402Facilitator`, validating its compatibility and retaining the same on-chain evidence rules. Public interface probes do not prove a funded settlement.

Send a stable `idempotency_key` with `bagseven_fetch` for an x402 resource. The daemon reserves one living entitlement credit and funds a stable isolated payer through the existing mandate's `execute`. The vault enforces its allocation and spending caps on-chain. Downstream merchant/origin/expiry policy belongs to the approved server signer; it is not an on-chain whitelist. Funding bytes, reserved gas and the payment job commit atomically before broadcast. EIP-3009 signatures commit before external verification or submission. Jobs use database locks, fenced leases and one unresolved allocation per payer. Tokens sent directly to a payer do not enlarge a job's authorized amount.

`bagseven_x402_payment(payment_id)` reconciles the job. Provider BFF routes under `/api/daemon/x402` expose scoped authority management, bounded payment lists, reconciliation and wallet recovery drafts. No private key is returned. Settlement needs a confirmed token transfer and matching authorization nonce; HTTP success is insufficient. Pending jobs reconcile in bounded batches. After confirmed authorization expiry, unused funding can return only to the original vault. Provider revocation stops new signing, but an existing signature can settle before expiry. Refunds restore the reserved access credit, not the vault's already-consumed spending quota. The Spending page displays recovery drafts for explicit wallet review; it never sends them automatically.

Run `node --env-file-if-exists=.env --import tsx scripts/test-x402-local.mjs` with local PostgreSQL and Anvil installed. It creates and deletes its own database and chain, exercises actual token transfers, lost responses, concurrent retries, revocation, refunds and crash recovery. It does not send public-network payments.

## Wallet-approved Fuji deployment and local upgrades

The existing Registry studio prepares public Fuji registry deployment transactions. Preparation verifies the currently connected wallet using a deployment-specific nonce/domain-bound signature, separate from account-wallet linking. The proof is single-use when issued, valid for ten minutes, bound to the signed-in verified email and website, and cannot authorize agent spending or replace the account wallet. Switching wallets requires preparing a new draft; an old draft cannot be sent from a different wallet. The wallet must use the public Fuji genesis, not an Anvil RPC sharing chain ID 43113. Review and approve the separate deployment transaction, then verify its sender, bytecode, runtime and two public-chain confirmations. The server stores the verified manifest without switching the local environment or enrolling any customers.

`pnpm upgrade:local-x402` is explicitly Anvil-only and requires the known development owner, local PostgreSQL, no active customer subscriptions and no unresolved x402 allocations. It backs up configuration, PostgreSQL and Anvil state before creating an EIP-3009 faucet token and a provider-bound mandate. Existing vault balances, old subscription records and grant history remain untouched; old local plan discovery entries retire and three fresh receipt plans are created. The signing journal and a local upgrade journal retain exact deployment bytes before broadcast. If Anvil was reset while PostgreSQL retained consumed nonces, the guarded development-only recovery aligns that nonce range without replaying old payments. A completed rerun verifies deployment identity and creates no additional funding, plans or grants. Backups and journals are private ignored files under `.data`; never use this command on Fuji or with production keys.

`pnpm mcp:tunnel` starts or reuses a local ngrok HTTPS tunnel, persists the active public origin, and starts MCP with a matching OAuth issuer. OAuth stays required. Use a current ngrok agent. Free ephemeral ngrok hostnames can change; keep the process running during a demo and use managed HTTPS hosting for production. The portable plugin generator `node scripts/package-mcp-plugin.mjs` uses the repository's logo and skill, excludes credentials, and verifies remote OAuth discovery. A verified native ChatGPT App ID in the private plugin state enables web-chat support; otherwise the package connects remote MCP in supporting desktop clients. Preserve installed plugin identity when updating a package, and leave old user connections intact unless removal is explicitly requested.

## Legacy email-link handoff

Current sign-in uses an email code in the same window. Already-issued magic links remain supported: the email callback creates the session cookie in the browser where the link opens. The original login page checks `/api/me` on mount, focus, page visibility and a bounded three-second polling interval. A verified session triggers a full navigation so middleware re-evaluates onboarding with the latest cookie. Authenticated requests to `/app/login` also redirect server-side. Return destinations are normalized by `appDestination` and restricted to app routes, excluding login/onboarding loops; query parameters are preserved. Opening the email in a different browser or profile cannot share that cookie.

Onboarding completion remains server-authorized: verified email and a signed wallet binding are required. A linked account can retry completion if its final request fails. Neither the session watcher nor UI state can manufacture a verified identity.

## Email and wallet onboarding

AccountWalletProvider is the console's shared authenticated profile state. ConnectWallet, onboarding and useOperator consume that same profile, refresh after binding, and update on focus or the cross-tab account-updated signal. Never infer a saved account binding from wagmi connection state. Wallet replacement preflight checks fresh inbox proof before issuing a signing challenge; POST rechecks expiry and preserves the database compare-and-set. OTP sign-in hydrates existing profiles and records fresh inbox proof when a binding already exists. Preview codes or magic links are returned only with explicit DEV_MODE=true outside production; public-Fuji local mode fails closed when email cannot be delivered. Legacy magic-link callbacks remain valid for already-issued links.

## Wallet approval coordination

Browser wallet actions use the shared SDK withWalletOperation coordinator. It rejects concurrent actions immediately and uses a same-origin Web Lock when available, so a second tab cannot queue another approval. Whole checkout, deployment, gas and spending actions retain the lock through their ordered wallet steps; no timeout releases a still-running request. Read existing accounts and the chain before requesting account access or switching networks. An RPC -32002 leaves a visible reminder; the user must finish the wallet request and acknowledge that reminder before an explicit new action. Acknowledging never cancels, resends or approves anything. Other origins and wallet-extension requests remain outside the site's control.

## Notification templates

Notifications share renderNotificationEmail in @bagseven/notify. sendNotify accepts an optional actionLabel or six-digit code and sends both HTML and plain text. Codes are rendered separately from metadata; do not place arbitrary HTML in message copy. Notification destination URLs must be HTTP(S) without embedded credentials. Authentication and MCP use the same renderer. Preview rendering is pure and does not send email.

## Customer billing documents

Migration 0022 adds private billing_documents snapshots and checkout token binding. PostgresBillingStore creates invoices in the checkout transaction; PostgresSubscriptionStore writes renewal invoices and payment status in the same transaction as the collection journal. Unique source keys make retries idempotent; conflicting receipt hashes or payers roll back the journal update. Public checkout polling never issues invoices or receipts. The customer portal lists its recent paid invoices. Server-authenticated customer tokens select the holder and billing contact; public document links are signed, invoice-specific and expire after 30 days.

GET /api/customers accepts bounded search and page parameters. GET /api/billing-documents accepts view=issued|purchases, status, customer and page, or an id for one document. Server sessions determine ownership; provider/holder query parameters cannot override it. Lists return 20 records, use provider/holder indexes, and have a five-second statement timeout. Private documents are visible to their provider, exact billed holder or authenticated billing email. A separate /billing/[id] route accepts a signed, expiring capability for exactly one paid document, with no wallet or account-management authority. Receipts are printable from /app/invoices/[id]. For isolated database verification, set BILLING_TEST_DATABASE_URL and run pnpm exec vitest run scripts/billing-documents.test.ts; it creates and removes its own schema and sends no chain transactions.

## Provider reporting

`GET /api/overview?days=7|30|90` is an authenticated console BFF endpoint. It derives ownership from `sessionHolder`, joins checkouts through their provider-owned plan, and returns aggregate counts plus bounded activity/recent/issues/plan lists. PostgreSQL repeatable-read keeps the report internally consistent. Migration 0021 adds provider/catalog, checkout creation-order and subscription issue indexes; report statements have a five-second timeout. The browser discards superseded requests when the period changes and preserves visible stale-data warnings on failed refreshes.

`GET /api/provider-checkouts?status=ALL|PAID|PENDING|EXPIRED|FAILED|CANCELLED&page=0&days=0|7|30|90` returns 20 rows and a count. A zero-day period means all time; overview drilldowns preserve their selected cohort. Pages are bounded to 0–500; narrow filters for older results. Both routes reject invalid input and return no-store responses. No raw billing email is exposed by the aggregate overview; customer identities are available only in authenticated provider checkout, customer and invoice management. Integration coverage in `scripts/test-subscription-persistence.mjs` creates its own database and checks cross-provider exclusion, cohort counts, expiry interpretation, daily series and pagination.

## Recording against public Fuji

The receipt app can use the live Fuji runtime without enabling `DEV_MODE`. Set `DEMO_PROVIDER_ID` to the provider's verified email and `DEMO_HOLDER` to the intended customer identity, then run `pnpm demo:dapp`. Purchase credits through the actual embed; never run `seed:demo` against public Fuji. A scan consumes one registry credit and keeps its result across refreshes. CSV, JSON and insights remain unavailable without their own feature entitlements; buying an OCR plan does not grant unrelated features.

The SDK observes already-connected injected-wallet accounts without opening an approval, follows account changes and disconnects, and checks the six-decimal payment-token balance before requesting a payment or subscription allowance. Prices identify recognized tokens by chain and contract; unknown contracts display their address instead of being labelled USDC. A reported pending wallet request is not proof that a payment was submitted. Reconcile any returned hash before retrying.

`pnpm mcp:tunnel` supports the local public-Fuji stack with `DEV_MODE=false` and requires `MCP_OAUTH_REQUIRED=true`. It refuses production execution; use managed HTTPS hosting there. When an ephemeral origin changes, restart MCP, regenerate the local plugin archive with `node scripts/package-mcp-plugin.mjs`, and update/reconnect the MCP client. Public discovery success alone does not prove a ChatGPT tool call or a paid agent operation.

## Customer billing identity and payment lifecycle

Use `await client.identify({ holder: authenticatedUser.id, email: authenticatedUser.verifiedEmail })` on the merchant backend. The secret key must remain on that backend. `email` is a trusted assertion by the authenticated SaaS, not a client-editable field or a claim of unique humanity. A valid email-shaped holder remains a backward-compatible contact default at token issuance. Opaque holder IDs require an explicit contact before live checkout. The signed customer token binds that contact to the holder; public checkout requests cannot replace it. Billing email remains in PostgreSQL and email delivery, never the Avalanche registry.

The default embed reads authorized accounts without a prompt and lets the customer choose the paying account when multiple accounts are available. Financial helpers validate that selected account against the wallet's authorized accounts and retain it for the payment-ownership signature. `walletProvider` and `walletAddress` let a host integrate its EIP-1193 connector without falling back to another injected wallet. `walletSlot` customizes presentation; supply the actual provider for the host connector. Neither the SDK nor the server accepts a customer wallet equal to the plan payout wallet. Newly compiled subscription contracts reject self-payment as well; existing immutable public contracts are not silently redeployed.

Checkout defaults to a 30-minute payment window (60 seconds to 24 hours may be explicitly configured). The database reuses an open, unpaid checkout for the same plan, holder, worker and return URL, without extending its deadline. The SDK remembers its checkout and submitted payment hash in session storage for recovery after reload. A background task durably expires sessions. An expired checkout cannot start a new payment, but confirmed payments made inside the original chain-time window may be reconciled afterward. Payments predating checkout or sent after expiry are rejected. Unpaid unreferenced sessions and their internal invoice drafts are purged 30 days after expiry in bounded batches. Paid, submitted-payment and subscription records remain available for reconciliation.

Customer and invoice lists show paid billing documents, not every abandoned checkout. Draft snapshots remain private transaction-recovery metadata until payment; first-period and renewal payments each queue exactly one receipt delivery. The billing portal shows recent paid invoices; it does not contain a test button that consumes credits without performing application work.

Migration 0023 adds billing contacts, lifecycle indexes and `billing_email_deliveries`. Payment recording and insertion of its unique email job share a PostgreSQL transaction. Workers claim at most ten deliveries with skip-locked leases and fence acknowledgements by lease ID. Resend receives a stable idempotency key and immutable payload. Email-provider acceptance is recorded as SENT; inbox delivery is not asserted. Log-only or unconfigured notifications never count as a delivered receipt. Once an uncertain job is 23 hours old, it enters RECONCILIATION_REQUIRED before the provider's 24-hour key window can lapse; verify provider history before any new send. See [Resend idempotency semantics](https://resend.com/docs/dashboard/emails/idempotency-keys).

Receipt links use a purpose-separated HMAC derived from `ENTITLEMENT_SUBJECT_SECRET`, bind one document and a 30-day expiry, and cannot read other documents. Preserve that secret across deployment. Shared documents have no-referrer/no-store/noindex protections and print/save-PDF support. Email never carries a wallet key or authority to spend. The configured `CONSOLE_URL` must be customer-reachable HTTPS in a hosted deployment; localhost links are only for local tests.

Run `BILLING_TEST_DATABASE_URL=<local-test-database> pnpm exec vitest run services/daemon/src/billing-lifecycle.pg.test.ts` for isolated-schema checkout concurrency, email fencing and expiry/purge tests. No real invoice emails or public-chain transactions are sent by that test. `node --import tsx scripts/test-subscriptions-local.mjs` verifies real contract collection, restart recovery, allowance revocation and cancellation on a temporary EVM, independently of public-Fuji acceptance.

## Provider API keys

Create provider-owned keys in Developers after email and wallet verification. `bgs_sk_…` is returned only by its creation response; the database stores a SHA-256 digest and a non-reconstructible hint, never the secret. `bgs_pk_…` is public and can be copied again. Keys have a name, expiry (1–365 days; default 90), last-used metadata and a revocation timestamp. Lists contain up to 100 records with active keys first. There are at most 10 active keys and 30 creations per provider per hour, serialized across replicas. Create a replacement, update your application, verify it, then revoke the old key. Revocation retains audit metadata and invalidates new requests plus customer tokens issued by that secret key; already-authorized in-flight work may finish.

Provider keys authorize public SDK billing and entitlement routes for that provider only, never internal daemon/admin routes. Customer holder IDs can repeat across providers: reads, consumes, cancellation, subscriptions and invoices must check the provider as well as the holder. Browser keys list public plans; private customer access and checkout details require a customer token or server secret. Provider keys cannot use the operator-only arbitrary credit-mint endpoint; use priced checkout. A signed provider selection cannot be replaced by a request header. Authentication checks PostgreSQL on each new request, including the issuing secret key for derived customer tokens, and fails closed on storage failure.

The console Developers API requires a verified email/wallet session, exact-origin mutation requests, and no-store responses. It never returns `BAGSEVEN_SECRET_KEY` or `DAEMON_AUTH_TOKEN`. Builder uses the provider’s active public key, including on hosted designs, instead of embedding the shared deployment key. Apply migration 0024 and rebuild database/daemon artifacts together. Legacy deployment API credentials are operator-only compatibility credentials; they are not provider-managed keys. If the previous Developers endpoint was deployed, rotate any shared secret it could return and update server integrations and MCP processes. Preserve the independent session, entitlement subject and delegated-key encryption secrets.

Shared HTTP services redact authorization and cookie headers in structured logs and return a generic message for unexpected internal errors; intentionally public validation and authorization errors remain descriptive.
